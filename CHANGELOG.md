# Changelog

## [3.0.0] - 2026-08-16

- **Fix**: operation type detection ignored a trailing slash, so an API that writes `/api/documents/{id}/` — the Django REST framework default — had no operation recognised as CRUD at all. Every method fell back to the raw operationId, which is why paperless-ngx ended up with `RetrieveAsync`, `DestroyAsync` and `PartialUpdateAsync` instead of `GetAsync`, `DeleteAsync` and `PartialUpdateAsync`. Of the current clients only paperless-ngx is affected; the others produce byte-identical output.
- **Fix**: a nested collection counted as the resource's own collection route, so `/ciphers/{id}/events` and `/organizations/{id}/events` both became `ListAsync` next to the real one. A route only counts as the collection now when no path parameter precedes the resource segment; vaultwarden's events client went from three indistinguishable `ListAsync` overloads to `GetCipherAsync`, `GetOrganizationAsync` and `GetOrganizationUserAsync`.
- **Fix**: the collision check that falls back to path-based naming compared the full parameter list, including optional parameters. Two methods whose only difference is an optional parameter cannot be told apart at the call site — `GetAsync(realm, groupId)` matched two overloads and simply would not compile for the caller. Collisions are now detected on the required parameters only, which removes the last 29 uncallable overloads (25 in keycloak, 4 in vikunja). No client has any ambiguous call left.
- **Fix**: any route ending in a parameter counted as this resource's item route, so `DELETE /documents/{id}/versions/{version_id}/` became a second `DeleteAsync` next to deleting the document itself. A route now only counts as the item route when the segment before the parameter is the resource itself; deeper routes keep their own name (`DeleteVersionAsync`).
- **Breaking**: a `GET` on the collection route is only named `List` when a collection actually comes back — a bare array, or the wrapper object a paginated API returns. Plenty of resources are a singleton: vaultwarden's `GET /api/config` returns one `ConfigResponseModel` and was called `ListAsync`, which tells the caller the opposite of what happens. 32 endpoints are renamed to `Get`, 24 of them in invoiceninja.
- **Breaking**: a leading `Put` in a method name becomes `Update`. `PUT` is an HTTP verb, not something a .NET caller says, and it means replace — vaultwarden's `TwoFactor_PutAuthenticator` reads as `UpdateAuthenticatorAsync`. `POST` is deliberately left alone: on a collection it means create, but on an action route (`.../raise-priority`) "create" would be wrong. Affects 42 methods.
- **Breaking**: bulk operations keep the name from their operationId instead of all collapsing to `Bulk`. A resource can have several — paperless-ngx has both `bulk_download` and `bulk_edit` on documents, which produced two `BulkAsync` overloads distinguishable only by request type, one of which returned a zip. Affects paperless-ngx (4 methods), invoiceninja (30), vaultwarden (8), immich (3), vikunja (3).
- **Breaking**: the resource name is stripped from method names on a word-by-word basis instead of only for a fixed list of prefixes, since the resource is already in the call path: `client.Correspondents.CorrespondentsListAsync()` becomes `client.Correspondents.ListAsync()` and `client.BankIntegrations.EditBankIntegrationAsync()` becomes `.EditAsync()`. Singular and plural count as the same word, only one side is stripped and never the whole name, so `DocumentsEmailDocument` keeps its `Document`. This renames a large part of the surface: paperless-ngx 161 of 164 methods, vaultwarden 210 of 213, invoiceninja 117 of 195, immich 67 of 186, keycloak 46 of 211, vikunja 4 of 121.
- `[[type_name_overrides]]` gained `applies_to` (`schemas`, `resources` or the default `both`). Overrides were applied to model type names and to resource client names alike, which is what makes `Oauth` become `OAuthClient` — but it also means renaming a schema that shares its name with a tag silently renames the client: paperless-ngx has both a `Tasks` schema (the redis/celery block of its status endpoint) and a `tasks` tag, so renaming the schema turned `client.Tasks` into `client.TaskQueueStatus`. Scope the override and both stay correct.
- Removed a hardcoded exception for one invoiceninja operation (`GetinvoicesAsync`) from the method naming. It compared a name that still lacked its `Async` suffix, so it could never match — dead code with a client name baked into the generator.

- Object schemas written inline as a property now get a generated type instead of collapsing to `object`. The spec describes their structure — paperless-ngx' `set_permissions` declares `view` and `change`, each with `users` and `groups` — and that structure was thrown away, leaving callers to guess an anonymous object. The type name is derived as `{Schema}{Property}`, identical structures share one type (paperless-ngx repeats the same permissions object across 16 schemas, hetzner and transip have around 25 each) and nesting is followed to any depth. Override the derived name with `[[inline_type_names]]`, which also keeps it stable if upstream reorders its schemas:

  ```toml
  [[inline_type_names]]
  property_filter = "^set_permissions$"
  schema_filter = "^Correspondent"   # optional
  name = "PermissionsSet"
  ```

  An inline object that describes a shape the spec already names is mapped onto that type instead of getting a duplicate: transip writes its `DnsEntry` inline inside a request wrapper, which produced a second, identical model called `RemoveDnsEntryDomainRequestDnsEntry`. Schemas that split into request/response variants are excluded from this reuse — there would be no single type to point at. This halved the number of new types for transip (25 to 12).

- New `--prune` flag (and `prune = true` config key) deletes generated `.cs` files in the models and client project directories that the current run did not write. Without it, files for operations removed from the spec keep lingering — regenerating paperless-ngx against a newer spec left three request classes behind for endpoints that no longer exist. Build output (`bin/`, `obj/`) is skipped and every deletion is printed. Off by default.
- **Fix**: binary responses are now detected by content type in general instead of a hardcoded list. Any non-textual media type (`application/zip`, `application/gzip`, `application/vnd.*`, ...) maps to `Stream`; textual types (`*/json`, `*/xml`, `text/*`, `*/yaml`, form-urlencoded) and wildcards (`*/*`) do not. Previously `application/zip` fell through to `Task<object>` and the response was read with `ReadAsStringAsync`, corrupting the download — hit by paperless-ngx `POST /api/documents/bulk_download/`.
- Responses declared as `type: string, format: binary` now map to `Stream` even when the spec pairs them with a JSON content type, which DRF-based specs do routinely.
- Primitive JSON responses now map to the matching CLR type instead of `JsonElement`. The mapping goes through the same `TypeMapper` that generates model properties, so response types and model properties can never drift apart. Enum schemas, objects and arrays are unaffected. This changes existing signatures — e.g. keycloak `GetAdminRealmsUsersCountAsync` now returns `Task<int>`, vaultwarden `InfoGetNowAsync` returns `Task<DateTimeOffset>` and vikunja `GetUserSettingsTotpQrcodeAsync` returns `Task<string>` — so regenerating a client is a breaking change for its consumers.
- **Fix**: array query parameters were serialized by calling `ToString()` on the array, so a request literally went out as `?task_type=System.String%5B%5D`. They now follow the parameter's OpenAPI `style`/`explode`: `explode: true` (the default for query parameters) repeats the key — `?task_type=a&task_type=b` — while `explode: false` joins the values with the separator for the style: `,` for `form`, a space for `spaceDelimited`, `|` for `pipeDelimited`. Both occur in practice: paperless-ngx declares `explode: false` on its 10 `__in` filters (`?id__in=1,2`) and `explode: true` on 9 others. Affected every client with an array parameter: hetzner (84), paperless-ngx (21), immich (4), keycloak (3), degiro (1).
- **Fix**: booleans in query strings were rendered `True`/`False` (the .NET default) instead of `true`/`false`, and dates went out in the invariant *culture* format (`08/13/2026 12:00:00 +02:00`) rather than ISO 8601. Both path and query values now go through one `FormatValue` helper: ISO 8601 for `DateTimeOffset`/`DateTime`/`DateOnly`/`TimeOnly`, lowercase booleans, invariant numbers.
- **Breaking**: path and query parameters now honour `format`. They went through a separate, format-blind mapper in which everything collapsed to `string`, `int`, `decimal`, `bool` or `string[]`. Parameters now use the same `TypeMapper` as models and responses, so `int64` becomes `long` (261 parameters, 260 of them hetzner — ids above 2^31 could not be expressed at all), `uuid` becomes `Guid` (230, mostly immich and vaultwarden), `date-time` becomes `DateTimeOffset` (52), `date` becomes `DateOnly` (32) and `array<integer>` becomes `List<int>` instead of `string[]` (22). Array parameters whose items are a named schema (enums) keep `List<string>`: the model type lives in the models namespace and an enum would serialize as its C# name rather than its wire value.
- **Breaking**: `format: date-time` now maps to `DateTimeOffset` instead of `DateTime`, in models, request classes, query parameters and responses. OpenAPI's `date-time` is RFC 3339 and therefore carries a UTC offset; `System.Text.Json` converts such a value into a local-time `DateTime`, discarding the offset and making the result depend on the time zone of the machine that happens to run the code. `DateTimeOffset` round-trips the original value. `format: date` keeps mapping to `DateOnly`. The invoiceninja client already worked around this with 36 `property_overrides` to `DateTimeOffset?`; those can be dropped. Every client that has a `date-time` field in its spec is affected (all except transip and hetzner's api spec).

## [2.4.1] - 2026-07-28

- **Fix**: the release workflow never published anything to NuGet. It ran `restore` → `build` → `Create GitHub Release`, with no `dotnet pack` and no `dotnet nuget push`, so `Apigen.Generator` on nuget.org was still at 1.0.1 while v2.2.0, v2.3.0, v2.3.1 and v2.4.0 all reported a successful release. Added the missing pack and push steps, and the `.nupkg` is now attached to the GitHub Release as well.

## [2.4.0] - 2026-07-28

- Generated project files now emit `<TargetFrameworks>` (plural) instead of `<TargetFramework>`, guarded by `Condition="'$(TargetFrameworks)' == ''"`. Two consequences: multi-targeting (e.g. `net10.0;net12.0`) is now a pure configuration change requiring no generator change, and a repo-level `src/Directory.Build.props` can override the target framework in a way that survives regeneration. MSBuild treats a single-valued `TargetFrameworks` identically to `TargetFramework`, so build output paths are unchanged (`bin/<config>/net10.0/`).
- **Fix**: the default value of `target_framework` was still `net8.0` (in both `GeneratorConfiguration` and `GeneratorOptions`), while every client repo shipped `net10.0` via an explicit override. Any new client generated without an explicit `target_framework` therefore got a project targeting a framework that reaches end of life on 10 November 2026. The default is now `net10.0`.
- Added `docs/target-framework-policy.md`, documenting which target frameworks generated clients ship with, why multi-targeting is off by default, and the dates on which the policy must be revisited.
- **Security**: bumped `Microsoft.OpenApi` and `Microsoft.OpenApi.YamlReader` from 3.5.1 to 3.9.0. 3.5.1 is affected by GHSA-v5pm-xwqc-g5wc (high severity: circular schema references may terminate OpenAPI parsing), patched in 3.5.4.
- **Behavior change in generated models** as a side effect of the parser upgrade: nullable properties that previously got no serialization attribute are now emitted with `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]`. Such properties are omitted from the request body when null instead of being serialized as `"prop": null`. For `Patched*` request models (PATCH endpoints) this is a fix — sending an explicit null typically clears the field server-side — but it is a semantic change for existing callers that relied on the previous output. Whether a client is affected depends on its spec; of the current clients only paperless-ngx changed (9 properties across 8 models). Regeneration is required for a client to pick this up.

## [2.3.1] - 2026-05-13

- **Fix**: DELETE (and GET) operations whose OpenAPI spec defines a request body now actually send that body. Previously `HttpClient.DeleteAsync(url, ct)` / `GetAsync(url, ct)` were used unconditionally — there is no overload that accepts content, so the body was silently dropped and the server typically responded `400/406 missing parameter`. Affected operations now generate `SendAsync(new HttpRequestMessage(HttpMethod.Delete|Get, url) { Content = content }, ct)`. Reproduces with TransIP `DELETE /domains/{name}/dns` (`RemoveDnsEntryDomainAsync`) — the `dnsEntry` body is now transmitted correctly. Affected clients: hetzner, immich, transip, vaultwarden, vikunja.
- Extracted shared `EmitRequestBodyContent` helper for body construction (used by POST/PUT/PATCH and now also DELETE/GET).

## [2.3.0] - 2026-05-13

- Generated client operations and interfaces now accept a `CancellationToken cancellationToken = default` parameter and propagate it to all `HttpClient` calls (`GetAsync`/`PostAsync`/`PutAsync`/`PatchAsync`/`DeleteAsync`) and to `HttpContent.ReadAsStringAsync`/`ReadAsStreamAsync`. Non-breaking for existing callers (default value).
- New generated `ApiException` (in `_ApiException.g.cs`) thrown on non-success HTTP responses. Inherits from `HttpRequestException` (non-breaking) and exposes `Method`, `Url`, `ResponseBody`, and `Headers`. Status code is set via the base constructor (`HttpRequestException.StatusCode`), so no shadowing.
- Generated operations now check `response.IsSuccessStatusCode` instead of `EnsureSuccessStatusCode()`. The error body is read only on failure (no memory regression on success — streams stay streamed, large success responses are unaffected).
- When `use_ilogger = true`, operations now distinguish three failure modes via dedicated catches, each with its own EventId before rethrowing:
  - Caller-initiated cancellation (`OperationCanceledException` with `cancellationToken.IsCancellationRequested == true`) → `LogDebugRequestCancelled` (EventId 1004, Debug).
  - `HttpClient.Timeout` (any other `OperationCanceledException`) → `LogErrorRequestTimeout` (EventId 3002, Error).
  - Transport failures (`HttpRequestException` that is not our `ApiException`: DNS, connect, TLS, etc.) → `LogErrorTransportFailure` (EventId 3003, Error).
- `ApiException` now also exposes `ContentHeaders` (`HttpContentHeaders`), giving callers access to `Content-Type`, `Content-Length`, `Content-Disposition`, etc. on error responses in addition to the existing status-line `Headers`.
- Added unit tests covering TOML parsing of `client.use_ilogger` (true/false/default) to lock in current loader behavior.
- Generator now resolves relative paths in the TOML (spec `path`, `output_path`) against the project root regardless of where it is invoked from. Project root = parent of the config file's directory when the config sits in a directory named `specs/`, otherwise the config file's directory itself. This means `dotnet run --project generator/src/Apigen.Generator -- --config transip/specs/transip.toml` now works from the workspace root, not just from `transip/`. New public helper `GeneratorConfiguration.ResolveProjectRoot(configPath)` and 4 unit tests covering the resolution rules.
