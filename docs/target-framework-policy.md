# Target framework policy

This document defines which .NET target frameworks Apigen-generated clients ship with,
and when that set changes. It applies to every client repo under `apigen-dotnet/`.

## Policy

> Generated clients target the **oldest .NET version that is still in Active support**.
> Versions in Maintenance support (security fixes only) are not added as targets, and
> versions past end of life are never targeted.

As of 2026-07-28 that resolves to a single target: **`net10.0`**.

## Why this, and not multi-targeting

A library that targets `net10.0` runs unchanged on net10, net11, net12 and beyond.
Only the *floor* determines which consumers you can serve — adding a higher target
framework does not reach a single extra consumer. It only lets the generated code use
newer BCL APIs, which requires TFM-conditional code (`#if NET12_0`) to be worth
anything. Apigen emits identical C# for every target, so multi-targeting would produce
functionally equivalent assemblies at the cost of a doubled build matrix, per-TFM
package references and a larger `lib/` folder in every package.

Multi-targeting is therefore off by default. The machinery supports it (see below) for
the day there is a concrete reason to use it.

## Why not net8.0

.NET 8 and .NET 9 both reach end of life on **10 November 2026**, and both entered
Maintenance support (security fixes only) in May 2026. Adding `net8.0` as a target would
buy a few months of relevance in exchange for permanent maintenance cost, and would put
an out-of-support framework in our packages shortly after. Consumers still on net8 who
need an Apigen client should pin to a package version released before their own upgrade,
or upgrade to net10 — which is LTS until November 2028.

## Review schedule

The policy is re-evaluated at every .NET release (each November). The binding dates:

| Date | Event | Action |
|---|---|---|
| 10 Nov 2026 | .NET 8 and .NET 9 EOL | No change — we do not target either. |
| Nov 2026 | .NET 11 released (STS) | No change — STS releases are not targeted. |
| Nov 2027 | .NET 12 released (LTS) | No change yet; net10 is in Active support until May 2028. |
| 14 Nov 2028 | .NET 10 EOL | **Bump the floor to `net12.0`.** |

Source of truth: <https://dotnet.microsoft.com/platform/support/policy/dotnet-core>

Missing the bump means publishing packages that target an end-of-life framework, which
downstream SBOM and supply-chain scanners will flag. The dates above are the trigger.

## How the target framework is configured

The value flows from generator config into every generated `.csproj`:

1. **Generator default** — `GeneratorConfiguration.TargetFramework` (`net10.0`). Applies
   to any client whose config does not override it.
2. **Per-client config** — `target_framework` in the client's `specs/*.toml`.
3. **Per-repo override** — `<TargetFrameworks>` in `src/Directory.Build.props`.

Generated project files emit the property as:

```xml
<TargetFrameworks Condition="'$(TargetFrameworks)' == ''">net10.0</TargetFrameworks>
```

`TargetFrameworks` (plural) is used even for a single target, so that switching to
multi-targeting is a pure configuration change rather than a code change in the
generator. MSBuild treats a single-valued `TargetFrameworks` identically to
`TargetFramework`; build output paths are unaffected (`bin/<config>/net10.0/`).

The condition means a repo-level `Directory.Build.props` always wins over the generated
default, and survives regeneration. That is the supported escape hatch for a repo that
must deviate from the policy.

To multi-target, set a semicolon-separated list at any of the three levels, for example
`net10.0;net12.0`. No generator change is required.

## Do not edit generated .csproj files

`.csproj` files under `src/` are generated by `Apigen.Generator` (see
`Generators/ClientGenerator.cs` and `Generators/ModelGenerator.cs`). Hand-edits are
overwritten on the next regeneration. Change the configuration instead.
